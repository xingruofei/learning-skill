# Skill 与知识库：内容如何划分

## 元信息

| 字段 | 值 |
|------|-----|
| 类型 | 对话整理 · 阅读笔记 |
| 来源 | Cursor 对话（基于淘宝 Skills 文 + Harness 文问答） |
| 创建日期 | 2026-06-21 |
| 关联文章 | [Harness不是目的，知识才是护城河](../articles/2026/06/20260618-harness不是目的-知识才是护城河-一个ai工程交付团队的知识沉淀实践.md) |

## 核心结论

1. **Skill = 行为契约 / 流水线**（做什么、按什么顺序、不能做什么）；**知识库 = 领域事实的单一来源**（业务/技术是什么、踩过什么坑）。
2. **早期可内嵌**：领域知识先放 Skill 的 `references/`，跑通后再抽到统一知识库；Skill 改为按需检索。
3. **Harness 文**：工作流可替换，知识可累积；Agent 查知识库要有预算，不能贪婪灌上下文。

## 分工对照

| | **Skill** | **知识库** |
|---|-----------|-----------|
| 本质 | AI 的行为契约 / 流水线 | 团队领域知识的单一事实来源 |
| 回答问题 | 做什么、按什么顺序、不能做什么 | 业务/技术是什么、为什么、踩过什么坑 |
| 变化频率 | 随工具链、模型、流程迭代 | 慢变，跨项目累积 |
| 生命周期 | 跟工作流绑定，可替换 | 独立于业务代码/项目 |
| 加载方式 | 触发时加载 SKILL.md + 按需 references | 决策点按需检索（RAG / 索引 / 渐进加载） |

## 放 Skill 里

- **工作流**（SKILL.md）：步骤顺序、输入输出、人工卡点、禁止项
- **确定性工程**（scripts/）：接口提取、工程初始化、编译验证——高精度环节用脚本
- **任务级模板**：只服务本流水线的代码模板、输出 schema、检查清单
- **编排逻辑**：子 Skill 拆分、审查 Skill 规则

类比：Skill ≈ 函数/类，封装「工作流 + 调用方式 + 局部约束」。

## 放知识库里

- **领域事实**（model / guideline）：SPU/SKU、字段映射、API 签名、架构说明
- **决策与陷阱**（decision / pitfall）：架构决策、已知反模式、跨项目复现的 Bug
- **流程知识**（process）：通用 SOP、对接规范——不绑某条 AI 流水线
- **大体量多源内容**：钉钉文档、Code Wiki、KBase RAG 召回
- **可向上提升的经验**：项目验证过的知识 → 团队/业务层（Harness 五层存储）

## 判断准则

```
换 Skill / 换模型还要用？        → 知识库
只在这条流水线某步生效？        → Skill
多个 Skill 共用同一份规则？     → 知识库；Skill 只留「查哪条」
体量大、常更新、需全文检索？    → 知识库；Skill 按需拉取
```

## 企业购对接示例

| 内容 | 放哪 | 理由 |
|------|------|------|
| 评估→方案→编码三步流程 | Skill | 流水线编排 |
| 接口提取用脚本、AI 校验 | Skill + scripts | 流程 + 确定性 |
| SPU/SKU 映射规则 | 知识库 | 多 Skill 共用 |
| 客户接口文档 | 项目输入 | 一次性输入 |
| 代码模板（SPI 实现类） | Skill references | 跟生码 Skill 绑定 |
| 推拉混写导致 API 幻觉 | 知识库 pitfall | 跨项目复现 |

## 常见误区

1. 知识库当 Skill references 副本 → 两处维护，很快不一致
2. 流程写进知识库 → Agent 检索到但不知何时执行
3. Skill 塞整本领域百科 → 上下文爆炸
4. 知识库无成熟度/衰减 → 过时规则继续误导 AI

## 推荐落地顺序

```
1. 先 Skill 跑通（workflow + 最小 references）
2. 发现跨 Skill 重复 → 抽到知识库
3. Skill 改为「触发 + 按需查询 + 约束输出」
4. 流水线 ARCHIVE 把新项目经验写回知识库
```
